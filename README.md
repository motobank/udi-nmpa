# udi-nmpa · 国家药监局 UDI 数据库纯后台查询模块

不打开浏览器、不装依赖、不需要登录，直接拿到医疗器械唯一标识（UDI）的注册信息。
封装成**可直接 import 的库**，供其它项目复用。

> 数据来源：<https://udi.nmpa.gov.cn/showListXXCX.html>（国家药品监督管理局 医疗器械唯一标识数据库）
> 接口逆向与限流实测定稿：**2026-11-19**，模块版本 **v1.0.0**

---

## 一、30 秒上手

```python
from udi_nmpa import UdiClient

c = UdiClient()                                  # 默认 2.5 秒/条，实测安全极限
rec = c.get_by_di("06971714900754")              # 按产品标识（DI）查

print(rec["医疗器械注册人/备案人名称"])           # 上海纽脉医疗科技股份有限公司
print(rec["产品名称/通用名称"])                   # 主动脉瓣球囊扩张导管
print(rec["型号规格/包装规格"])                   # BAV25
```

返回的 dict 用**中文列名做键**（和官网表格一一对应），另附 `rec["raw"]` 保留接口原始字段
（`deviceRecordKey` 在里面，跳转详情页要用）。

命令行也能直接跑：

```bash
python cli.py 06971714900754                  # 单个查
python cli.py 06971714900754 --json           # JSON 输出
python cli.py -f data/条码列表.txt -o out.csv  # 批量查 + 导 CSV
python cli.py -f list.txt -o out.csv --resume  # 断点续跑
python cli.py 主动脉瓣 --limit 20              # 模糊查，最多 20 条
python cli.py -f list.txt --interval 3        # 改间隔（保守值）
```

## 二、接口档案（逆向结论）

官网那个页面的搜索框只是"壳子"，真正的数据由 **jqGrid 表格通过 AJAX** 去拿。抓出来就是：

```
POST https://udi.nmpa.gov.cn/getDeviceList.html
Content-Type: application/x-www-form-urlencoded

query=<关键词>&searchType=1&page=1&rows=50&sidx=&sord=asc&_search=false
```

| 参数 | 说明 |
|---|---|
| `query` | 关键词。普通搜索填标识/产品名/企业名；高级搜索填 Lucene 表达式 |
| `searchType` | `1` = 普通搜索；`2` = 高级搜索（`字段:值 AND ...`） |
| `page` / `rows` | 页码 / 每页条数 |
| `sidx` / `sord` | 排序字段 / 方向，留空即可 |
| `_search` | 固定 `false` |

**返回**（截取真实响应）：

```json
{
  "records": 1, "total": 1,
  "rows": [{
    "deviceRecordKey": "06971714900754202302071146247",
    "primaryDeviceId": "06971714900754",
    "agencyName": "GS1",
    "deviceCount": 1,
    "companyName": "上海纽脉医疗科技股份有限公司",
    "productName": "主动脉瓣球囊扩张导管",
    "specification": "BAV25",
    "deviceEndDateStatus": "--"
  }]
}
```

### 认证情况（实测，别再重复试）

- **完全开放**：无登录、无 Cookie、无 token、**连 Referer 都不需要**。
  实测用 `curl/8.0` 的裸请求（不带 Referer、不带 Content-Type）照样返回 200 正常 JSON。
- **GET 也能用**：`getDeviceList.html?query=xxx&searchType=1&page=1` 直接返回同样内容。
- 页面里的 `acw_tc` / `JSESSIONID` Cookie 是 WAF 和容器的会话标记，**不传也不影响**。

### 字段映射

| 接口原始字段 | 中文列名 |
|---|---|
| `primaryDeviceId` | 最小销售单元产品标识 |
| `agencyName` | 医疗器械唯一标识编码体系名称 |
| `deviceCount` | 最小销售单元中使用单元的数量 |
| `companyName` | 医疗器械注册人/备案人名称 |
| `productName` | 产品名称/通用名称 |
| `specification` | 型号规格/包装规格 |
| `deviceEndDateStatus` | 是否退市 |
| `deviceRecordKey` | （仅内部用）详情页跳转键 |

### 怎么找到这个接口的（可复用套路）

1. 用调试模式 Chrome 打开页面，CDP 读 DOM，发现表格是 jqGrid（`class="els-jqGrid ui-jqgrid-btable"`）。
2. jqGrid 必有 `url:` + `postData:`。直接 `curl` 拉页面源码和 `app.js`，grep `getDeviceList`。
3. 找到初始化代码里的 `url`、`postData`、`mtype`，参数就齐了。
   逆向原始证据留在 `docs/page.html`、`docs/app.js`。

## 三、限流实测数据（本模块最有价值的部分）

`udi.nmpa.gov.cn` 前面确实有墙：DNS 里 CNAME 指向
`rnf4k6mo6slm7icf8dl2nscfeqixilmn.yundunwaf5.com`（**阿里云盾 WAF**），
但拦截不是 WAF 拦截页，而是**应用层限流**：`HTTP 429` + `{"message":"搜索过于频繁，请稍后再试"}`。

### 实验一：阶梯并发（3 个标识轮转，档间冷却 30 秒）

| 并发数 | 请求 | 成功 | 429 | P50 耗时 |
|---|---|---|---|---|
| 10 | 10 | **1** | 9 | 341ms |
| 20 | 20 | **1** | 19 | 415ms |
| 30 | 30 | **1** | 29 | 592ms |
| 40 | 40 | **1** | 39 | 702ms |
| 50 | 50 | **1** | 49 | 1101ms |

**每档恒定只过 1 个** —— 并发在这里毫无意义。且并发越高越慢（排队，不是网络拦截）。

> ⚠️ **重要更正（2026-11-19 二次验证）**：这里"只过 1 个"是**测法污染**的结果，不是服务端规则。
> 本脚本每档开始前会先跑一次 `probe_once()` 探测，**那次探测已经吃掉 2 个名额中的 1 个**，
> 紧接着的并发爆发自然只剩 1 个名额。
> 补测（空闲 22 秒后纯净爆发）证明真实规则是 **同时放行 2 个**：
>
> | 同时发 | 结果 |
> |---|---|
> | 2 个 | 200, 200 —— 全过 |
> | 3 个 | 200, 200, **429** |
> | 5 个 | 200, 200, **429, 429, 429** |
>
> 教训：**做限流实验时，探测请求本身也是消耗配额的**，不能紧贴着爆发跑。

### 实验二：间隔扫描（单线程）

| 间隔 | 成功率 | | 间隔 | 成功率 |
|---|---|---|---|---|
| 0.2s | 2/5 | | 1.5s | 4/5 |
| 0.5s | 2/5 | | **2.0s** | 4/5 |
| 0.8s | 4/5 | | **2.5s** | **5/5** ✅ |
| 1.0s | 2/5 | | **3.0s** | **5/5** ✅ |

### 实验三：串行精扫，1.5→2.6 每 0.1 秒一档（每档 5 条）

以「**请求发出时刻**」为基准算间隔，不是"响应回来再 sleep"（后者会把 350ms 响应耗时算进周期，结果偏乐观）。

| 间隔 | 成功 | 状态码序列 |
|---|---|---|
| 1.5s | 3/5 | 200, 200, **429, 429**, 200 |
| 1.6 ～ 2.4s | 4/5 | 200, 200, **429**, 200, 200 |
| **2.5s** | **5/5** | 全 200 |
| **2.6s** | **5/5** | 全 200 |

**分水岭精确卡在 2.4 与 2.5 秒之间。** 1.6~2.4 这九档全是同一个形态（每 5 条必掉第 3 条），
几乎没有随机性 —— 说明这是**确定的配额规则**，不是抖动。

### 实验四：2.5s 复测 3 轮 × 8 条

第 1 轮 7/8（受上一轮残余影响），第 2、3 轮均 **8/8**，合计 **23/24 = 95.8%**。
2.5 秒可稳定跑，但**没有余量**。

### 实验五：429 之后要缓多久

连发 5 条打爆后探测：`+0.1s 429 → +0.5s 429 → +1.2s 200`。

**429 是"软拒绝"不是惩罚，1.2 秒就恢复。** 所以遇到 429 不必长等，
短退避重试（1.5/3/4.5 秒阶梯）即可逼近极限，不用为了害怕而把间隔拉到 5 秒以上。

### 实验六：模拟真实扫码节奏（10 个真实条码）

节奏：每 **0.3~1.0 秒**随机"扫"到一个新码，**立刻新开线程发出，不等上一个返回**。
即"多条线依次循环、扫完就走"的真实工况。用 10 个真实 DI（同企业 15 条记录中取前 10 条）。

| 轮次 | 策略 | 成功 | 总耗时 | 峰值并发 |
|---|---|---|---|---|
| 轮 A | 裸测，每条只发一次 | **4/10（40%）** | 6.1 秒 | 1 |
| 轮 B | 失败退避重试直到拿到内容 | **10/10（100%）** | **26.9 秒** | **2** |

**这组数据比前面所有测试都更贴近业务真相：**

- 扫码 10 个只花 **5.9 秒**（平均 0.65s/个），但后台要 **26.9 秒**才补齐 → **产能错位 4.5 倍**
- 裸测 6 个当场 429 失败，用户看到的就是"扫了没反应"
- 最后一条（第 4 个扫的）等了 **23.5 秒**才拿到
- **峰值并发始终只有 2** —— 开了 10 个线程，实际同时在途最多 2 个。
  再次印证：**新线程不创造吞吐，只会制造 429 噪音**
- 带重试的实际吞吐 = 10 条 / 26.9s ≈ **22.3 条/分钟**，已贴近理论天花板 24 条/分钟

**结论：能"支持"，但不能"实时"。**
扫码可以多快都行（先进队列），但每条内容平均要等 2.5 秒才回来。
所以业务上必须是 **"扫进去 → 后台排队补 → 补到就回填"**，绝不能做成"扫一个当场查一个、查不到就报错"。

### 实验七：并发上限到底几个（纯净爆发，空闲 22 秒后）

| 同时发 | 结果 | 放行数 |
|---|---|---|
| 2 个 | 200, 200 | **2** |
| 3 个 | 200, 200, 429 | **2** |
| 5 个 | 200, 200, 429, 429, 429 | **2** |

**结论：同时最多放行 2 个，与开几个线程无关。** 第 3 个起立刻 429。
随后每 2.5 秒回补 1 个名额，所以长期平均仍是 24 条/分钟。

「能开 2 个线程」≠「吞吐翻倍」：2 个并发只在**瞬间**有用（把首屏两条内容同时拿回来），
持续跑起来依然被 2.5 秒/条的节奏卡死。

### 实验八：A/B 双通道消费模型（10 个码，FIFO 队列）

模型：两个线程当两条通道，从 **FIFO 队列**取码；**谁拿到正确数据谁立刻再接一个**，
不设人为间隔；遇 429 等 1.0 秒再试。（`bench/dual_lane.py`）

| 指标 | 结果 |
|---|---|
| 成功 | **10 / 10** |
| 总耗时 | **22.6 秒**（平均 2.3 秒/条） |
| 实际请求数 | **44 个**（其中 429 共 **34** 个） |
| 有效率 | **23%**（10 条内容 / 44 次请求） |
| 通道分布 | A 消化 5 条，B 消化 5 条（**零饥饿**） |
| 实测吞吐 | **26.5 条/分钟** |

**关键观察：两条通道是"成对"放行的。**

```
0.7s  [B] ✓   [A] ✓      ← 开局 2 个令牌，两条同时过
7.3s  [A] ✓   [B] ✓      ← 同一瞬间
13.7s [B] ✓   [A] ✓      ← 同一瞬间
16.3s [B] ✓   [A] ✓
22.4s [B] ✓   22.6s [A] ✓
```

因为名额是"2 个 / 5 秒窗口"整批回补的，所以总是一对一对地通过，
两条通道各拿一半，**天然公平，不会出现谁饿死**。

**结论：**

- 双通道**确实比 10 线程快**（22.6s vs 26.9s），而且完全公平 → **生产就用双通道**
- 但**吞吐并没有变高**：22.6 秒已经贴着 24 条/分钟的天花板（开局白送 2 个令牌所以略超）
- **代价是 77% 的请求是废的**（34/44 打在 429 上）。这买不来速度，纯属噪音
- 若要干净：429 之后不要固定 1 秒乱撞，而是**按"上一次成功时刻 + 2.5 秒"推算下次开闸**再试，
  请求数可从 44 压到 12 左右，耗时基本不变

### 实验九：A/B/C 三通道（首次出发错峰 0.3 秒，毫秒级时间戳）

规则同实验八，但开 **3 条通道**，首次出发依次错开 0.3 秒（A@0ms、B@302ms、C@602ms），
记录每次请求的毫秒级发出/返回时刻与在途并发数。（`bench/three_lane.py`）

| 指标 | 双通道（实验八） | **三通道（实验九）** |
|---|---|---|
| 成功 | 10/10 | **10/10** |
| 总耗时 | 22.6s | **22.429s** |
| 请求数 | 44 | **59**（多 15 个） |
| 429 数 | 34 | **49** |
| 有效率 | 23% | **17%**（更差） |
| 通道分布 | A 5 / B 5 | A 4 / B 3 / C 3 |
| 峰值在途 | 2 | **3** |

**决定性证据：C 通道的第一次请求就被拒了。**

```
+   0ms  [A] 200  耗时463ms   ← 占掉名额 1
+ 302ms  [B] 200  耗时368ms   ← 占掉名额 2
+ 602ms  [C] 429  耗时135ms   ← 名额已满，第 3 条通道首次出发即被拒
```

**结论：**

- **三通道没有变快**（22.429s vs 22.6s，差异在噪声范围内），但**多打了 15 个废请求**
- 峰值在途并发确实到过 **3** —— 说明"3 个连接可以同时开着"，但**只有 2 个能拿到 200**。
  所以限制的**不是连接数/线程数，而是"每窗口 2 个成功名额"**
- 名额是**成对同时放**的：成功时刻成对出现（464/670、6755/6830、10274/10618、16452/16454、22408/22428）
- **通道数超过 2 就是纯浪费。生产环境用 2 条通道，多的那条只会制造 429**

### 实验十：「卡点开闸」——按预测的开闸时刻出手（最终推荐方案）

既然名额是**按窗口整批放**的，就不该"每秒撞一次 429"，而应该**只在开闸时刻出手**。
实现：A/B 两条通道共享一个"放名额的闸"，每周期一次性放 2 个，周期长度可自适应
（遇 429 拉长、连续成功收紧）。（`bench/pacer.py`）

**参数扫描结果（同一 10 个码）**

| 周期配置 | 耗时 | 请求数 | 429 数 | 有效率 |
|---|---|---|---|---|
| 5.0s 固定 | 30.6s | 12 | **2** | 83% |
| 5.5s 固定 | 31.2s | 12 | **2** | 83% |
| **5.8s 固定** | **23.6s** | **10** | **0** | **100%** |
| 自适应（5.5 起，自动伸缩） | 24.0s | 10 | 0 | 100% |

**5.0 和 5.5 都会撞墙，5.8 干净。** 真实窗口约 **5.8 秒 / 2 个名额**。
一旦撞了 429，自适应会把周期推到 6.5s，反而把总耗时拖到 31 秒 —— **撞墙的代价远大于慢一点**。

5.8s 固定周期的实际发射时刻，整齐得可以当尺子用：

```
+    0ms  [A] ✓   [B] ✓
+ 5800ms  [A] ✓   [B] ✓
+11600ms  [A] ✓   [B] ✓
+17400ms  [B] ✓   [A] ✓
+23200ms  [B] ✓   [A] ✓
```

**四方案总对比（同样 10 个码）**

| 方案 | 耗时 | 请求数 | 429 | 有效率 | 评价 |
|---|---|---|---|---|---|
| 10 线程乱抢 | 26.9s | 44+ | 多 | — | ❌ 有饥饿 |
| A/B 双通道（1s 盲等重试） | 22.6s | 44 | 34 | 23% | ⚠️ 快但脏 |
| A/B/C 三通道 | 22.4s | 59 | 49 | 17% | ❌ 纯浪费 |
| **卡点开闸 5.8s** | **23.6s** | **10** | **0** | **100%** | ✅ **推荐** |

**结论：用 1 秒的代价，换掉 77% 的废请求。**

底层原因也清楚了：盲等重试是"机会主义"——名额一释放立刻抢到，延迟最低，但 34 次都打空；
卡点开闸是"守时"，请求干净，但万一相位错开就要等整个周期。
**生产环境选后者**：多 1 秒无所谓，服务端压力小、长期更稳定、策略收紧时也不容易被盯上。

> 实现细节坑：周期必须按「上次开闸时刻 + 周期」累加推进，不能写成「现在 + 周期」。
> 后者会把每轮的请求耗时（~0.7s）累加进周期，5 轮就白丢 3.5 秒。

### 实验十一：改用「注册证号」检索 —— 一次查询抵 25 次

此前全部用产品标识（DI）检索。本次换成注册证号 `国械注准20223131010`。

**先查字段清单**：`GET https://udi.nmpa.gov.cn/deviceField.html` 返回 33 个可检索字段，
其中第 29 个是 `REGCARD_NAME`（注册证/备案证号）。

**四种写法实测：**

| 写法 | 结果 |
|---|---|
| 普通搜索 `searchType=1`，`query=国械注准20223131010` | 200，但 **records=0**（搜不到） |
| 高级 `REGCARD_NAME:国械注准20223131010` | **HTTP 500**（语法错） |
| 高级 `REGCARD_NAME:"国械注准20223131010"` | **HTTP 500**（语法错） |
| **高级 `REGCARD_NAME:("国械注准20223131010")`** | **200，records=25** ✅ |

**语法铁律**：是 `字段:("值")`，**括号和引号缺一不可**，缺了不是返回空，而是 **HTTP 500**。
这是从页面 `buildQuery()` 源码里读出来的：`advField值 + ":" + "(" + '"' + 值 + '"' + ")"`。

**查询效果：**

```
国械注准20223131010
→ 上海微创医疗器械（集团）有限公司
→ 冠脉雷帕霉素洗脱钴基合金支架系统
→ 25 条 UDI 记录（FBP2513 / FBP2518 / ... / FBP4033，共 25 个规格）
```

**关键发现：**

- **一次注册证号查询 = 25 条 UDI**，2 次请求（翻页）、**6.1 秒**跑完
- 换成按 DI 逐条查，同样 25 条要 **25 × 5.8 秒 ≈ 145 秒**、25 次请求
- **效率差 24 倍。有注册证号就别用 DI 一条条查**
- 但**返回体里不含注册证号本身**（只有 8 个标准字段），所以证号要自己记着
- **单页上限 15 条**：请求 `rows=50` 也只给 15 行，25 条必须翻 2 页
- **翻页已实测无重复**：25 条（2 页）零重复；另取 32 条（3 页，15+15+2）也零重复，
  说明服务端分页顺序稳定，可以放心用 `search_all()` / `get_by_regcard()` 自动翻页
- **翻页成本**：每页 1 次请求，按 5.8 秒周期算，3 页约 12 秒；150 条（10 页）约 58 秒

**业务含义**：扫码枪扫到的通常是 DI（一物一码），扫不到注册证号；
但如果单据/台账上有证号，用它批量取全规格会快一个数量级。
反过来，拿到一个 DI 后可以**先用 DI 反查到企业+产品名，再按证号批量补全同族规格**。

**补充实测：普通搜索的检索范围到底覆盖哪些字段（四种写法全试）**

| 普通搜索关键词 | 结果 |
|---|---|
| `国械注准20223131010` | **0 条** |
| `20223131010` | **0 条** |
| `械注准20223131010` | **0 条** |
| `国械注准 20223131010`（带空格） | **0 条** |
| `冠脉雷帕霉素洗脱钴基合金支架系统`（产品名，对照组） | **150 条** ✅ |

**结论：普通搜索的死角就是注册证号，任何写法都搜不到。**
它的检索范围只有三样：**产品标识（DI）/ 产品名称 / 企业名称**。
想按证号查，绕不开 `searchType=2`。

顺带发现一个坑：**按产品名查会串到别家**——
「冠脉雷帕霉素洗脱钴基合金支架系统」返回 **150 条**，是多家企业的同名产品混在一起；
而按注册证号查只有 **25 条**，全是同一证号下的同族规格。**要干净就必须用证号。**

### 结论汇总（可直接抄进别的项目）

- **硬极限：2.5 秒 1 条**（= 2 条 / 5 秒滑窗，24 条/分钟，1440 条/小时）
- **推荐：3.0 秒 1 条**（留 0.5 秒余量，实际业务够用）
- **并发无用**，别开线程池（同时最多放 2 个成功，第 3 个起 429；开 50 个也只过 2 个）
- **429 可安全重试**，1.2 秒即恢复，不会封号/IP
- **生产形态 = 双通道 + FIFO 队列**（10 码 22.6 秒跑完、零饥饿），不要开 10 个线程乱抢
- **通道数 2 是上限**：3 通道 22.4s vs 2 通道 22.6s，快不出来，反而多 15 个废请求
- **最佳实践 = 双通道 + 5.8 秒一轮、每轮放 2 个名额**（10 码 23.6 秒、10 次请求、0 个 429）
- **有注册证号就用注册证号查**：`REGCARD_NAME:("证号")`，一次 6 秒拿全 25 个规格，比按 DI 逐条快 24 倍
- **普通搜索搜不到注册证号**，必须走 `searchType=2` 且括号引号齐全，否则 HTTP 500
- 200 次量级请求、4 分钟内**未触发任何 IP 级封禁**

> 注：以上均为**凌晨 00:13~00:56 的实测数据**，工作时段策略可能更严，生产环境建议用 3 秒。

## 六、代码里几个"必须这样写"的坑

1. **必须绕开系统代理**。本机设了 `http_proxy`，走代理会拿到被代理伪造的状态码
   （曾把"连接被拒"误报成 502）。库内默认 `proxy=False`，用空 `ProxyHandler` 直连。
2. **429 响应没有 `Retry-After` 头**，退避时间只能自己定（用 1.5 秒起步即可）。
3. **限速要按"请求发出时刻"算**。写成"响应返回后再 sleep"会让真实周期变成 `间隔 + 响应耗时`，
   测出来的"极限"偏乐观，上线就翻车。
4. **`search` 是模糊匹配**。用 DI 精确查时可能带回多条，`get_by_di()` 内部已做精确优先筛选。
5. **表格有隐藏副本**。官网页面上 `.queryContent` 等输入框有多份隐藏副本，
   用 DOM 取值时若用全局选择器会取到空的那份（本模块不走 DOM，不受影响，但做前端自动化要注意）。
